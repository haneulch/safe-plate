# 편의점·가공식품 판정 기능 설계안

> 상태: 설계 검토 단계 (구현 미착수) · 2026-07-11

## 1. 목표 / UX

여행자가 편의점·마트에서 **상품 바코드를 스캔하면 자기 프로필 기준 신호등 판정**을 받는다.

- "이 삼각김밥에 새우 들어있나?" → 원재료·알레르기 표시 기반 즉시 판정
- 식당 판정과 동일한 UI 문법(안심/조건부/주의 + 사유), 동일한 판정 엔진 재사용
- 편의점은 어디에나 있으므로 위치 검색보다 **스캔이 핵심 진입점** (매장 지도는 후순위)

## 2. 데이터 파이프라인 (전부 실존 API 확인됨)

```
EAN-13 바코드
  │ ① C005 바코드연계제품정보 (식약처)
  ▼    바코드 → 품목보고번호(prdlstReportNo), 제품명, 제조사, 소비기한
품목보고번호
  │ ② C002 식품(첨가물)품목제조보고(원재료) (식약처)
  ▼    원재료 문자열 (예: "밀가루, 계란, 대두유, 새우분말…")
원재료 텍스트
  │ ③ 기존 추론 사전 + 원재료 전용 규칙 → MenuTag[] (알레르겐 태그)
  ▼
Menu 객체로 변환 → 기존 judgeMenu(profile, menu) 그대로 판정
  │ ④ (보조) 전국통합식품영양성분정보(가공식품) 표준데이터
  ▼    나트륨/당류/포화지방 등급 채움 (음식 DB와 동일한 집계 방식)
신호등 판정 + 사유
```

### 필요 API (활용신청 목록)

| # | API | 발급처 | 용도 | 비고 |
|---|---|---|---|---|

| ② | [식품(첨가물)품목제조보고(원재료) (C002)](https://www.data.go.kr/data/15062098/openapi.do) | 식약처 | 품목보고번호→원재료 목록 | 알레르겐 판정의 근거 |

## 3. 아키텍처 통합

기존 구조 그대로 확장 — 서버 DB 불필요 원칙 유지.

```
src/app/api/products/[barcode]/route.ts   # C005→C002 프록시 + 24h LRU 캐시
src/lib/mfds/client.ts                     # 식품안전나라 API 클라이언트 (server-only, 별도 키)
src/lib/mfds/mapper.ts                     # 원재료 텍스트 → Menu 변환
src/lib/inference/ingredients.ts           # 원재료 전용 규칙 (라벨 표기 관용구:
                                           #  "○○ 함유", "대두유", "새우분말", "밀가루" 등)
src/lib/nutrition/processed-db.ts          # 가공식품 영양 등급 사전 (빌드타임 집계)
src/app/(main)/scan/page.tsx               # 스캔 화면 + 결과 카드
```

- **판정**: 원재료→태그 변환 후 `judgeMenu` 재사용. 원재료는 라벨 실표기라 추론 confidence를 `high`로 둘 수 있음 (메뉴명 추정보다 신뢰도 높음) — 단 교차오염 문구("같은 제조시설…")는 `cross` 태그로 변환.
- **바코드 스캔**: 브라우저 `BarcodeDetector` API (Chrome/Android OK) + Safari/iOS 폴백으로 `zxing-wasm`. 카메라 권한 거부 시 바코드 숫자 직접 입력 필드.
- **키 관리**: `.env.local`에 `MFDS_API_KEY` 추가. 식품안전나라는 일 쿼터가 작으므(기본 1,000) 캐시 필수 — 상품 데이터는 불변에 가까워 24h+ TTL 적합.

## 4. 리스크 / 한계

1. **C005 커버리지**: 국내 품목보고 제품 위주. 수입 과자·PB 일부 미등록 → 수입식품 DB 폴백 + "정보 없음 — 라벨의 알레르기 표시를 확인하세요" 안내 (안심카드 UX와 동일한 안전 기본값).
2. **원재료 텍스트 품질**: 괄호 중첩("혼합제제(밀, 대두)"), 비율 표기 등 파싱 규칙 필요. 알레르기 22종 표시 의무 덕에 주요 알레르겐은 명시적으로 등장 — 규칙 기반으로 충분.
3. **iOS 스캔**: BarcodeDetector 미지원 → zxing-wasm 번들(+~300KB). 수용 가능.
4. **판정 책임**: 식당과 동일하게 "참고용 사전 스크리닝, 실물 라벨 확인" 고지 유지.

## 5. 단계 제안

- **P1 — 바코드 판정 (핵심 가치)**: C005+C002 연동, 스캔 UI, 원재료 파서, 판정. 편의점 위치 없이도 완결된 기능. *규모: 2~3일*
- **P2 — 카페·베이커리 분류 노출**: TourAPI cat3(A05020900 카페 등) 배지 + 필터 칩. 신규 API 불필요. *규모: 반나절*
- **P3 — 편의점 지도**: 상가정보 API로 주변 편의점 표시. *규모: 1일*
- **P4 — 푸드QR**: 신제품 QR 직접 스캔 경로 추가.

## 6. 착수 전 필요한 것 (사용자 액션)

1. 식품안전나라(foodsafetykorea.go.kr) 회원가입 → Open API 키 발급 (C005, C002)
2. data.go.kr에서 수입식품 제품DB 활용신청 (선택)
3. 가공식품 영양 표준데이터 JSON/CSV 다운로드 (음식 데이터 때와 동일 방식)
